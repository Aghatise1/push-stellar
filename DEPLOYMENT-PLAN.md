# Push deployment plan

Updated 25 September 2026. This plan keeps the existing Django account system and uses Supabase as managed PostgreSQL. It does not add Supabase Auth, so Push has one user record, one session system and one Google sign-in flow.

## Current state

- Local Django application: working.
- Email/password registration: pending details are stored with a password hash; the application user is created only after the six-digit code is verified.
- Verification and recovery delivery: implemented; real inbox delivery requires protected SMTP settings on the local preview and hosted service.
- Google OAuth: configured locally; the client secret remains server-side.
- Shared database: connected to Supabase PostgreSQL and migrated through `core.0006_pendingregistration`.
- Production static-file serving: prepared with WhiteNoise.
- Render deployment blueprint: prepared in `render.yaml`.
- Real payments: deliberately not enabled.

## Build order

### 1. Create the shared Supabase database

1. Create one Supabase project in a region close to the first users.
2. In the project's **Connect** dialog, choose **Session pooler** and copy its PostgreSQL connection string. It uses port 5432 and suits a persistent Django web service.
3. Put it directly into the hosting provider's protected `PUSH_DATABASE_URL` setting. Never paste it into chat, HTML, JavaScript or source control.
4. Run `python manage.py migrate` on the hosted service.
5. Create test accounts through the website and test pending registration, code verification, sign-in, sign-out and password recovery.

The browser does not need a Supabase anonymous key for the current architecture. A Supabase service-role key must never be placed in browser code. User uploads can use a private Supabase Storage bucket later, through short-lived signed links.

### 2. Publish a private test deployment

Use the included Render blueprint for the first review deployment. Required protected settings are:

- `PUSH_DATABASE_URL`: Supabase pooler URL.
- Render supplies its public hostname automatically. Set `PUSH_ALLOWED_HOSTS` and `PUSH_ORIGIN` only when adding a custom domain.
- `PUSH_SECRET_KEY`: generated by the host.
- `PUSH_GOOGLE_CLIENT_ID` and `PUSH_GOOGLE_CLIENT_SECRET`.
- SMTP settings for verification and recovery email.

Before opening the deployment to testers, run both release checks from the host shell:

```text
python manage.py check --deploy
python manage.py check_release --live-stellar
```

The second command verifies the protected configuration, Supabase connection, applied migrations, official Stellar testnet USDC issuer and live Horizon network. It prints only pass/fail information and never prints credential values. Render uses `/healthz/` to confirm that the running service and database are available.

The free Render service is suitable for demonstrations and invited testing. It sleeps after inactivity, so its first request can be slow. It is not the final production tier.

### 3. Make Google sign-in public

1. Add the hosted origin to the Google OAuth authorised JavaScript origins.
2. Add `https://HOST/accounts/google/login/callback/` as an authorised redirect URI.
3. Keep the OAuth client secret only in protected host settings.
4. During invited testing, add testers in Google's OAuth audience settings.
5. Before a public launch, publish the app homepage and privacy policy on the verified domain, then complete Google's required production checks.

### 4. Enable real email

Use a transactional-email provider with a verified sending domain. Store the SMTP password in protected host settings; never put it in the repository or browser. The same `PUSH_EMAIL_*` variables work locally and on the hosted service. Supabase's default Auth sender is not used by this Django architecture and would not remove the need for custom SMTP for external testers.

### 5. Invite a small test group

Start with 5–20 named testers. Use fictional jobs and testnet/simulated payments. Monitor account creation, email delivery, access control, error logs and mobile layouts. Do not accept real money during this phase.

### 6. Production gate

Move to an always-on paid web instance when real users need predictable response times. Add backups, monitoring, administrator MFA, legal pages, data deletion/export, moderation, incident response and an independent security review. Real payments require provider onboarding, signed webhooks, idempotency, reconciliation, refunds and supported-country decisions.

## Expected cost path

- Local development: $0.
- Supabase Free: suitable for an early test database within its quotas.
- Google sign-in: no separate hosting or database; keep requested scopes to basic profile and email.
- Render Free: suitable for a review demo, with sleep/cold-start limitations.
- Transactional email: a free allowance is usually sufficient for a small invited test; a domain is still required for a professional verified sender.
- Domain: normally the first unavoidable annual purchase.
- Public production: expect an always-on application host, database plan, email and monitoring to become paid as usage and reliability requirements grow.

AWS can host the application, database, email, files and monitoring, but it is a large collection of services rather than a single website host. Its new-customer free plan is useful for learning and prototypes; it ends after six months or when credits run out. Push does not need that operational complexity for its first invited test. Moving later is manageable because the application already uses portable Django and PostgreSQL rather than provider-specific browser logic.
